# ESP32 与后端通信要求

## 1. 范围

本文浓缩前端和 C5 对现场 ESP32 的通信要求。ESP32 只通过 MQTT 与后端通信，不直接连接 Web 或 C5，也不处理语音识别。

当前仅完成需求整理，尚未按新增水枪协议修改代码。用户结论和外部待确认事项统一记录在 [问题汇总](open-questions.md) 中。

实际硬件是普通 ESP32，PlatformIO 继续使用 `esp32dev`。为兼容前端协议，对外标识使用 `device_id=greenhouse_001_s3`、`site_id=greenhouse_001`；名称中的 `_s3` 只是协议命名，不代表真实芯片型号。

## 2. 通信链路

```text
Web/C5 -- HTTP、SSE --> 后端 -- MQTT command --> ESP32
Web/C5 <-- HTTP、SSE -- 后端 <-- MQTT ACK、遥测、状态 -- ESP32
```

ESP32 应只订阅自身的 `command`，并发布：

- `command_ack`：命令最终处理结果。
- `telemetry`：传感器值和执行器状态。
- `status`：在线状态，retain，并配置离线 LWT。
- `capabilities`：真实硬件能力，retain。

主题统一采用：

```text
smartagribrain/v1/devices/{device_id}/command
smartagribrain/v1/devices/{device_id}/command_ack
smartagribrain/v1/devices/{device_id}/telemetry
smartagribrain/v1/devices/{device_id}/status
smartagribrain/v1/devices/{device_id}/capabilities
```

设备协议按前端扩展执行。`command`、`command_ack`、`telemetry`、`status`、`capabilities` 和 LWT 当前统一使用 QoS 1；Broker 的离线队列与过期配置仍需后端按 Q-020 回复。

## 3. ESP32 需要实现的命令

### 3.1 普通执行器命令

继续支持原子 `set` 命令：

- `pump`：整数百分比 `0..100`。`0` 立即停泵，非零值输出对应 PWM。
- `grow_light`：整数百分比 `0..90`。
- `pan`：水平舵机目标角度。
- `tilt`：俯仰舵机目标角度。

普通水泵和水枪已确认共用 GPIO26 上的同一个实体水泵：水泵负责抽水并输送到水枪。两类命令必须经过同一个水泵控制函数和安全状态，不能分别写 PWM。

### 3.2 水枪目标命令

前端新增了一种复合命令，核心结构为：

```json
{
  "command": {
    "operation": "target_position",
    "target": "position",
    "position": {
      "ground_range_mm": 850,
      "bearing_deg": -12.5
    },
    "water_gun": {
      "mode": "static",
      "spray_enabled": true,
      "simulation_only": false,
      "pump_control_percent": 50,
      "session_id": null,
      "sequence": 7,
      "spray_schedule": "timed",
      "spray_duration_seconds": 113,
      "spray_ends_at": 1784620913000
    }
  }
}
```

字段含义：

- `ground_range_mm`：水枪原点到目标地面点的水平距离，单位 mm。
- `bearing_deg`：方向角，`0` 为正前方，负数向左，正数向右。
- `mode`：`static` 或 `dynamic`。
- `spray_enabled`：是否喷水；为 `false` 时必须停泵。
- `simulation_only`：为 `true` 时允许计算和 ACK，但禁止物理开泵。
- `pump_control_percent`：水泵目标百分比。
- `session_id`、`sequence`：动态会话标识和递增序号。
- `spray_schedule`：`continuous` 或 `timed`。
- `spray_duration_seconds`：定时时长，范围 `1..86399` 秒。
- `spray_ends_at`：Unix Epoch 毫秒截止时间。

该复合结构已被确认为正式水枪接口，需要同步扩展统一标准。普通 `pump` 继续保留；直接 `pan`、`tilt` 只作为本机调试能力，不作为前端正式水枪接口。

## 4. 水枪运行场景

### 4.1 静态持续喷水

设备先停泵，移动舵机，等待稳定，再按目标百分比开泵。水泵持续运行到收到有效停泵命令、目标变化、网络断开或设备故障。

### 4.2 静态定时喷水

设备校验时长和绝对截止时间，移动舵机并稳定后开泵，同时建立本地单调时钟截止点。到期后必须自行停泵，不能只依赖后端补发停止命令。

相同 `command_id` 重发时只能重发原 ACK，不能重复动作或重新开始计时。

### 4.3 修改目标

目标变化时必须先停泵，再移动舵机。超出机械范围或无法完成坐标映射时应拒绝命令，不能静默截断到另一个位置。

### 4.4 动态模式

动态模式进入时默认停泵。同一 `session_id` 内只接受递增的 `sequence`；退出会话立即停泵并清空会话状态。

前端计划最高以 5 Hz 更新目标。设备保留 3 秒动态安全超时，但 Web heartbeat 是否会转换为 MQTT 尚待前端/后端回复，见 Q-017。

### 4.5 C5 语音控制

C5 只负责语音交互和用户确认。后端确认后生成与 Web 相同的 MQTT 命令，ESP32 不实现第二套 C5 协议。

普通“开关水泵”走 `pump` 命令；“向目标喷水”走最终确认后的水枪命令。定点喷水必须先得到用户确认。

## 5. 设备处理顺序

1. 校验 JSON、协议版本、设备 ID、命令 ID、来源和有效期。
2. 完成基础身份校验后，若是停止请求，优先停泵并取消定时器。
3. 检查重复命令；已处理命令只重发首次 ACK。
4. 校验模式、会话序号、时间字段、数值范围和模拟标志。
5. 目标变化时先停泵。
6. 使用明确标注为虚拟数据的保守映射计算水平和俯仰角，并检查安全范围。
7. 非阻塞等待 800 ms 临时稳定时间。
8. 建立定时或动态安全状态后再开泵。
9. 确认控制输出已写入后发布最终 ACK。

停止优先不等于跳过身份校验。未经设备 ID、协议和命令来源校验的数据不能驱动 GPIO，否则任何能访问 Broker 的客户端都可以造成拒绝服务。

## 6. 本地安全要求

- 上电、重启、WiFi/MQTT 断开和看门狗异常时关泵。
- 定时喷水同时使用绝对截止时间和 `millis()` 单调计时。
- NTP 未同步或截止时间已过时，不得启动定时喷水。
- 动态会话超时后关泵；具体保活协议待确认。
- `simulation_only=true` 时禁止物理开泵。
- 普通水泵与水枪共用统一仲裁，安全停止优先级最高。
- 水枪非零功率四舍五入后低于 40% 时暂时提升到 40%；`0` 始终停泵。
- 距离功率公式和 40% 启动值均为临时数据，必须通过实测重新标定。
- 解析失败不能启动水泵；若设备已处于喷水状态，应按最终确认的故障策略处理。
- 水泵、舵机目标和运行状态必须从同一状态对象产生遥测和 ACK，避免上报值与实际输出来源不同。
- MQTT 使用持久会话和 QoS 1；任何重复消息都必须经过命令 ID、有效期和动态序号校验，不能把 QoS 1 当作“只投递一次”。

## 7. ACK、状态和能力

ACK 至少包含：

- `schema_version`、`command_id`、`device_id`、`acknowledged_at`。
- `state`：只使用 `executed` 或 `rejected`。
- 原命令摘要和 `actual_value`。
- 拒绝时提供稳定的 `error.code`。
- 水枪命令应回显已接受的位置、模式、序号、定时参数和实际水泵输出。

当前硬件没有舵机位置反馈和水流传感器，因此 `executed` 表示 PWM/舵机控制值已写入且状态机无错误，不能表述为已经测得真实角度或水流。前端展示语义仍需对方接受，见 Q-019。

`capabilities` 需要声明普通水泵、补光灯、水平/俯仰舵机，以及最终确认后的水枪、定时喷水、动态更新频率和模拟模式能力。

## 8. 需要进行的代码改造

确认协议后，ESP32 侧需要完成以下工作：

1. 扩展命令模型和 JSON 解析，支持位置、水枪模式、定时和动态会话字段。
2. 建立独立的非阻塞水枪状态机，负责转向、稳定等待、开泵、定时停止和动态超时。
3. 增加目标坐标到两个 SG90 角度的标定映射，并对越界目标明确拒绝。
4. 将普通泵命令和水枪泵控制合并到同一个 GPIO26 安全出口。
5. 扩展 ACK、遥测和能力声明，报告水枪当前状态与停止原因。
6. 扩展幂等缓存，使重发不会重新转向、开泵或重置定时器。
7. 增加静态持续、静态定时、目标变化、动态序号、断线、过期和重复命令测试。
8. 为命令接收、每级校验、安全停止、舵机移动、稳定等待、定时器、水泵输出和 ACK 发布增加带错误码的串口日志。
9. 按第 9 节的注释规范整理所有新增和受影响代码，使参数、状态和完整控制环路可以直接从代码中读懂。

本轮不修改代码。外部待确认项不影响协议模型和状态机的设计，但真实联调前必须完成 Q-017、Q-019、Q-020、Q-021。

## 9. 代码注释与环路说明要求

后续实现必须满足以下可读性要求：

- 每个命令结构字段都说明来源、类型、单位、合法范围、是否允许 `null` 以及非法时的错误码。
- 每个运行状态字段都说明由哪个步骤写入、在哪些条件下清除，以及断网或停止时的值。
- 每个控制函数都说明功能、全部参数、参数单位与范围、返回值、错误结果、GPIO 副作用和安全前置条件。
- 临时标定点、距离功率公式、40% 最小 PWM 和 800 ms 稳定时间必须标注为非实测数据，不能只写成没有来源的常量。
- MQTT 回调只负责解析和入队；硬件动作由主循环中的状态机执行。注释必须解释为什么不能在回调中阻塞。
- 主循环按“网络维护、MQTT 处理、安全计时、状态机推进、传感器采集、遥测发布”分段，并说明每段输入、输出和执行顺序。
- 水枪状态机按“接收、基础校验、业务校验、幂等检查、停泵、转向、稳定等待、建立保护、开泵、ACK”标出阶段和转换条件。
- 串口日志使用与状态机一致的阶段名、`command_id`、`session_id` 和错误码，便于从日志还原完整执行过程。
- 注释必须解释协议语义、安全原因和硬件限制，不能只重复代码表面动作。

## 10. 前端要求中的不合理或不完整之处

- 实际芯片为普通 ESP32，却使用带 `_s3` 的设备 ID，技术上可运行但容易误导维护人员，代码和部署文档必须注明。
- 水枪复合命令和新增公共字段已被接受，但统一 v1 标准必须同步升级，避免后端仍按旧原子协议校验。
- 同时允许 UUID 和十进制 `command_id` 会增加校验复杂度，必须限制长度和字符并按完整字符串幂等。
- 当前坐标映射、距离功率公式和 40% 最小启动值都是虚拟或临时数据，不能宣传为真实标定结果。
- Web 心跳不转发到设备，却要求设备按 MQTT 静默三秒退出动态模式，两端会产生状态分歧。
- 原 MQTT 库已替换为支持 QoS 1 发布和持久会话的 ESP-IDF MQTT 客户端。QoS 1 会增加确认开销、重复和离线积压，因此后端仍需明确 Broker 队列策略。
- 没有位置或流量反馈时，ACK 只能表示输出已写入，前端必须使用准确文案。
- “看到 `spray_enabled=false` 就先停泵”不能早于基础身份校验，否则会形成未授权停机入口。
- 后端定时状态只保存在内存中不可靠；要求 ESP32 本地定时停止是合理且必要的，不应删除。

## 11. 验收重点

- 普通水泵和水枪控制不会争抢 GPIO26。
- 持续、定时和动态模式都遵守先停泵、后转向、稳定后开泵。
- 定时到期、动态失联、断网和重启均能可靠关泵。
- 重复、过期、越界、乱序和模拟命令不会造成意外喷水。
- ACK 与实际写入的控制输出一致，Web/C5 在 ACK 前不显示已执行。
- C5 和 Web 最终使用同一份后端 MQTT 契约。
