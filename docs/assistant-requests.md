# 用户问题与处理记录

最后同步日期：2026-07-22。

本文件记录用户向 Codex 提出的任务、问题和处理结果。每项使用 `R-XXX` 编号；`来源编号` 保留用户原始编号。状态只能使用“待处理”“处理中”“已解决”“部分解决”或“已阻塞”。未执行验证不得标为已解决。

`open-questions.md` 仅记录必须由用户、前端、后端或外部团队确认的事实。本文件发现这类依赖时，会引用对应 Q 编号。

## 使用格式

```md
### R-XXX：简短标题

- 来源编号：用户原始编号；无则写“无”。
- 状态：待处理 / 处理中 / 已解决 / 部分解决 / 已阻塞
- 用户问题：
- 目标与验收标准：
- 涉及范围：
- 处理过程：
- 修改内容：文件路径和变更摘要；无修改时写“未修改”。
- 验证结果：命令、测试、构建或人工核查；未验证时说明原因。
- 结论：
- 遗留事项：无则写“无”。需要外部答复时引用 `open-questions.md` 的 Q 编号。
```

### R-033：动态保活序号的语义与前端同步

- 状态：已解决。
- 用户问题：为什么 heartbeat 每次都需要递增服务器序号；服务器只有一个，为什么还要递增；并解决由此产生的问题。
- 结论：`sequence` 不是用于区分服务器实例，而是用于区分同一服务器连续发出的控制状态。MQTT QoS 1 允许重复投递，网络也可能造成延迟或乱序；ESP32 只能以单调递增序号判断一条 heartbeat 是否比已执行状态更新。若没有该序号，旧包或重复包可能错误地延长水泵运行时间。
- 修改内容：后端仍作为唯一序号权威，每次有效 heartbeat 递增 `sequence`；前端收到 heartbeat 响应后同步本地最大序号，且不会用较旧响应覆盖已经收到的较新目标位置。后续位置更新会带上最新序号，因此不会再因本地序号滞后被后端拒绝。
- 涉及文件：`前端/backend_api/water_gun_service.py`、`前端/src/App.vue`。
- 验证结果：前端生产构建已通过。真实设备场景仍需验证断网重连、重复 MQTT 包和 3 秒安全停泵。
