### Q-029：动态模式指定一次位置却重复转动或未到最终角度

- 状态：已实现代码修复，待重新部署 Web/后端并烧录 ESP32 后完成实体复测。
- 已确认原因一：浏览器动态目标更新和每秒 heartbeat 曾分别递增同一个 `sequence`，并发时最终目标可能因序号重复被后端拒绝。
- 已确认原因二：Web/后端曾允许小于 300 mm 或大于 1200 mm 的距离，但 ESP32 只接受 `300..1200 mm`；页面显示新位置时，设备可能已经拒绝并保留旧角度。
- 已确认原因三：ESP32 在前一目标的 800 ms 稳定等待中收到相同目标保活时，曾取消待执行命令并再次写两个舵机 PWM。
- 已确认原因四：动态模式关闭喷水时，ESP32 曾错误清除动态会话和最后序号，使延迟到达的旧目标可能绕过乱序校验并驱动舵机回跳。
- 修复结果：
  - MQTT 动态序号只由后端在同一把锁内生成；REST 仍兼容旧 `sequence` 字段，但不再使用浏览器数值。
  - Web 动态目标请求改为串行发送；请求期间只保留最新目标，heartbeat 和 SSE 不得覆盖本地正在选择的目标。
  - Web 指针距离钳制为 `300..1200 mm`，后端 REST 同样拒绝超出设备能力的距离。
  - ESP32 对稳定等待期间的相同目标保活只替换待完成命令并保留原截止时间，不再次写 GPIO27/GPIO13 PWM。
  - 动态模式即使关闭水泵也保留 `session_id` 和最后 `sequence`；只有退出动态模式才清除乱序校验状态。
- 验证：前端生产构建通过；后端 165 个测试和 7 个子测试通过；PlatformIO `esp32dev` 构建通过。实体复测仍需使用更新后的三个端。

### Q-017：动态模式的设备保活方式

- 状态：已实现。Web 每 1000 ms 调用 heartbeat；后端在锁内递增同一动态会话的 `sequence`，把当前 `target_position` 进入 MQTT 队列；ESP32 收到合法新序号后刷新 3 秒安全超时。
- 序号所有权：Web 不再生成 MQTT 序号，动态目标更新和 heartbeat 都由后端统一分配，避免并发重复。
- 相同目标：设备端保活不会重复写舵机 PWM；若命令到达时舵机仍在稳定等待，只替换待完成命令并保留原截止时间。
- 失联保护：页面关闭、网络中断或后端停止后不再产生保活，ESP32 在 3 秒内自动停泵。
- 剩余验收：需要从实体 ESP32 采集连续 heartbeat、断网 3 秒停泵和最终 ACK 日志。

### Q-020：设备上行 MQTT QoS 与后端会话配置

- 状态：部分实现。ESP32 和后端均已使用 QoS 1 与持久会话；后端已实际连接 EMQX。EMQX 托管实例的离线队列上限和消息过期策略尚未取得可验证配置，仍不能宣称已完成旧命令积压治理。
- 问题：后端/Broker 如何配置持久会话、离线队列上限和消息过期，避免 QoS 1 旧命令积压？
- 分析结论：
  - QoS 1 增加一次 PUBACK、少量带宽、Broker 会话状态和重复消息概率，但不会因为使用 QoS 1 就无法接收消息。
  - 当前消息量较低，即使动态控制达到 5 Hz，ESP32 和正常 Broker 通常也能承受。
  - 网络不稳定或设备离线时，持久会话可能积压旧消息；命令必须有过期时间、序号和幂等处理。
  - QoS 1 是“至少一次”，不是“只执行一次”；设备仍必须依靠 `command_id` 防止重复动作。
  - 原 PubSubClient 的普通上行 `publish()` 为 QoS 0；设备代码现已改用支持 QoS 1 发布和持久会话的 ESP-IDF MQTT 客户端。
- 最终决定：当前阶段 `command`、`command_ack`、`status`、`capabilities` 和 `telemetry` 全部使用 QoS 1；允许将 PubSubClient 替换为支持 QoS 1 发布的 MQTT 客户端。
- 后端必须提供：Broker 产品和版本、设备会话是否持久、离线队列条数/字节上限、消息过期策略，以及后端订阅各主题时使用的 QoS。
- 用户答复：当前先统一使用 QoS 1，并同步修改文档和设备代码。
- 历史外部反馈：此前本机 Mosquitto 的监听、队列上限和会话结论已不再适用，不能作为当前 EMQX 部署依据。
- 当前实现：后端与 ESP32 本机配置均启用 EMQX `mqtts://`、QoS 1 和持久会话；后端已成功连接并订阅，ESP32 已通过编译。命令仍通过 `expires_at`、动态序号和 `command_id` 幂等处理拒绝旧消息或重复消息。

- 临时舵机稳定时间：800 ms，必须使用非阻塞状态机等待。
- 安全限制：垂直轴任何写入都强制限制在实体安全的 5 至 60 度，上电初始角为 5 度。距离到角度的线性关系仍必须标注为未完成落点标定；在喷水实验完成前不能宣称能够准确瞄准目标。
- 用户补充答复：垂直舵机真实旋转范围只有 5 至 60 度；5 度时水枪平行向前，60 度时水枪竖直向上。

### Q-018：同一水泵和临时功率规则

- 状态：已实现实测分段模型，旧临时线性规则已停用。
- 普通水泵与水枪共用 GPIO26 上的同一个实体水泵，由水泵抽水输送到水枪。
- 两类命令必须共用控制函数、运行状态、安全停止和 PWM 输出。
- 距离功率关系采用 `改/前端` 的两段实测拟合：低段截止于 `30%`、`24.26 cm`，高低两段分别使用已记录的实测斜率和截距。
- 停泵命令始终输出 `0%`；需要喷水时，拟合结果限制在实测有效范围 `24%..100%`，旧的 `40%` 临时最小启动值不再参与后端计算。
- Web、REST 和 MQTT 继续传递既有毫米距离与百分比功率字段，单位和通信契约没有变化。

## 已知实现缺口

以下内容是代码与目标契约之间已确认的差异，不需要猜测，也不新增外部问题编号：

- 当前 `SEND_INTERVAL_MS=5000`，实际是 5 秒，已与正式标准一致。
- 状态和 LWT 已按精简契约确定为 retained 快照，不要求 `message_id`。
- 遥测已有 `quality`；裸板阶段允许 0、-127 和浮空 ADC 值，仅用于验证通信链路。
- 当前 ACK 缓存容量为 50 条，但没有独立的 10 分钟保留计时。
- 水枪坐标、舵机稳定时间、水泵 40% 最小启动值和距离功率关系都没有实测。
- 后端本机配置已启用 EMQX MQTT 传输并完成连接验证，水枪控制已使用真实下发路径；尚未取得实体 ESP32 的完整命令 ACK 采样。
- Web heartbeat 已转换为每秒一次的设备可见 MQTT 保活；后端或页面停止后由 ESP32 的 3 秒动态超时停泵。实体断网复测尚未完成。
- Web 与 C5 尚未完成 ACK 物理反馈语义、超时、离线和拒绝文案的统一。

这些项目应由对应的前端、后端、C5 或 ESP32 任务修复、确认或标定。若任何团队希望改变目标契约，必须先在本文件新增问题、写清修改原因、兼容影响和验收方式，不能只在代码中单方面改变字段。
