### Q-017：动态模式的设备保活方式

- 状态：用户已答复，待前端/后端确认。
- 问题：Web heartbeat 是否会被后端转换为 ESP32 能收到的 MQTT 保活消息？
- 原因：如果 heartbeat 只存在于 HTTP 层，ESP32 按“3 秒无 MQTT”停泵时会与 Web 会话状态不一致。
- 设备侧要求：动态喷水必须有设备可见的保活；建议后端每秒发布带同一 `session_id` 和递增 `sequence` 的当前目标/保活命令，ESP32 保留 3 秒安全超时。
- 用户答复：当前无法确认，需要向前端开发者提问并提出合理要求。

### Q-020：设备上行 MQTT QoS 与后端会话配置

- 状态：设备侧已确认全部使用 QoS 1，待后端提供 Broker 会话配置。
- 问题：后端/Broker 如何配置持久会话、离线队列上限和消息过期，避免 QoS 1 旧命令积压？
- 分析结论：
  - QoS 1 增加一次 PUBACK、少量带宽、Broker 会话状态和重复消息概率，但不会因为使用 QoS 1 就无法接收消息。
  - 当前消息量较低，即使动态控制达到 5 Hz，ESP32 和正常 Broker 通常也能承受。
  - 网络不稳定或设备离线时，持久会话可能积压旧消息；命令必须有过期时间、序号和幂等处理。
  - QoS 1 是“至少一次”，不是“只执行一次”；设备仍必须依靠 `command_id` 防止重复动作。
  - 原 PubSubClient 的普通上行 `publish()` 为 QoS 0；设备代码现已改用支持 QoS 1 发布和持久会话的 ESP-IDF MQTT 客户端。
- 最终决定：当前阶段 `command`、`command_ack`、`status`、`capabilities` 和 `telemetry` 全部使用 QoS 1；允许将 PubSubClient 替换为支持 QoS 1 发布的 MQTT 客户端。
- 后端必须提供：Broker 产品和版本、设备会话是否持久、离线队列条数/字节上限、消息过期策略，以及后端订阅各主题时使用的 QoS。
- 用户答复：当前先统一使用 QoS 1，并同步修改文档和设备代码。

## 已确认

### Q-001 至 Q-005：硬件与 GPIO

- 状态：已确认。
- 云台使用两个 SG90，独立稳定 5 V 供电并与 ESP32 共地。
- GPIO27 控制水平轴，GPIO13 控制俯仰轴。
- GPIO14 控制补光灯，GPIO26 控制水泵。

### Q-006 至 Q-010：执行器基础参数

- 状态：已确认。
- 两轴软件范围暂为 `0..180` 度，上电初始角均为 90 度。
- GPIO14 高电平有效，补光灯范围为 `0..90%`。
- GPIO12 WS2812 暂时保留，但不响应补光灯 MQTT 命令。
- 旧 `farm/test/control_cmd_888` 及 `panAngle/tiltAngle` 只属于历史调试协议，正式联调使用 v1 主题。

### Q-011：GPIO26 水泵驱动

- 状态：已确认。
- GPIO26 高电平有效，允许 1 kHz PWM，范围为 `0..100%`。
- 普通持续泵控制不设置最长运行时间，但停泵命令和网络安全停止始终有效。

### Q-012 与 Q-013：硬件型号和协议命名

- 状态：已确认。
- 实际硬件是普通 ESP32，PlatformIO 保持 `esp32dev`，不能按 ESP32-S3 编译目标配置。
- 对外协议按前端命名使用 `device_id=greenhouse_001_s3`、`site_id=greenhouse_001`。
- 名称中的 `_s3` 只是协议标识，不代表真实芯片型号。该命名具有误导性，但不妨碍 MQTT 工作；代码必须添加说明，避免维护人员选错工具链。
- 此结论取代此前 `device_id=sensairshuttle_001` 的约定。

### Q-014：水枪命令结构

- 状态：已确认。
- 按前端要求正式采用复合 `target_position`，在一条命令中携带目标位置、水枪模式、水泵、定时和动态会话。
- 普通 `pump` 命令继续保留；直接 `pan`、`tilt` 不作为前端水枪正式接口，可保留为本机调试能力。

### Q-015：命令公共字段

- 状态：已确认。
- 按前端协议扩展统一标准：接受 UUID v4 和十进制字符串 `command_id`，接受 `source=edge_voice`，加入 `site_id`，并加入水枪相关错误码。
- 仍须保证命令 ID 非空、长度受限、字符合法，并按完整字符串执行幂等。

### Q-016：临时坐标标定

- 状态：已确认采用保守虚拟标定，尚未完成真实标定。
- 临时水平映射：`bearing_deg=0` 对应 90 度；仅接受 `-45..45` 度，线性映射到水平舵机 `60..120` 度。
- 临时距离映射：仅接受 `300..1200 mm`；使用三个虚拟点 `300 mm -> 110 度`、`750 mm -> 90 度`、`1200 mm -> 70 度` 分段线性插值。
- 临时舵机稳定时间：800 ms，必须使用非阻塞状态机等待。
- 安全限制：代码、能力声明和串口日志必须明确标注 `UN_CALIBRATED_PLACEHOLDER`。超出范围直接拒绝；在完成实测标定前，这组数据不能宣称能够准确瞄准目标。
- 用户答复：暂无真实数据，可先使用能运行的保守虚拟数据，但代码和注释必须明确其非实测性质。

### Q-018：同一水泵和临时功率规则

- 状态：已确认。
- 普通水泵与水枪共用 GPIO26 上的同一个实体水泵，由水泵抽水输送到水枪。
- 两类命令必须共用控制函数、运行状态、安全停止和 PWM 输出。
- `ground_range_mm / 1700 × 100` 是临时算法，不是实测模型，代码和日志必须明确标注。
- 非零目标经四舍五入后低于 40% 时提升到 40%，确保达到临时最小启动 PWM；ACK 返回实际应用值。`0` 始终表示停泵。
- 该最小值和距离功率算法后续必须通过真实水泵测试重新标定。

### Q-022：非法命令与诊断日志

- 状态：已确认。
- 无法解析、协议版本错误或设备 ID 不匹配的报文只记录并忽略，不驱动 GPIO。
- 通过基础身份校验但水枪业务字段非法时，若正在喷水则先停泵，再发布拒绝 ACK。

### Q-024：当前阶段 MQTT QoS 决策

- 状态：已确认。
- ESP32 的命令订阅、ACK、遥测、在线状态、能力声明和 LWT 全部使用 QoS 1。
- 设备 MQTT 会话使用持久会话；命令仍通过有效期、动态序号和 `command_id` 幂等防止旧消息或重复消息造成二次动作。
- 原 PubSubClient 已替换为 ESP-IDF MQTT 客户端，设备上行按 QoS 1 进入异步 outbox 并等待 PUBACK。
