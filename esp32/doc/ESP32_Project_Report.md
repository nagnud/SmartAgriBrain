# ESP32 工程项目说明报告

## 1. 项目概述

本工程是整个项目中的 ESP32 边缘端代码，主要负责农业环境数据采集、设备本地控制、无线联网和 MQTT 数据上报。

从整体项目角度看，ESP32 不是单独存在的测试板程序，而是系统的“感知与执行入口”。它直接连接土壤湿度、光照、温度、CO2 等传感器，并控制 LED 灯带、水泵等执行设备。上层平台、服务器或 dayu200 端并不直接接触真实硬件，而是通过 ESP32 发布的数据和接收的控制指令来感知农田环境、展示状态、触发控制策略。因此，这部分代码决定了整个系统能否获得稳定、真实、连续的现场数据，也决定了云端控制命令能否真正落到硬件动作上。

## 2. ESP32 部分在整体项目中的作用

ESP32 部分承担整个项目的边缘节点角色，是硬件层和云端/应用层之间的桥梁。

在完整系统中，传感器和执行器位于最底层，服务器、可视化界面、数据分析模块和控制端位于上层。ESP32 运行在现场，负责把底层硬件采集到的模拟量、数字量或串口数据转换成统一的数据格式，再通过 WiFi 和 MQTT 推送到服务器。同时，它也订阅控制主题，接收来自上层系统的控制指令，并将这些指令转换为 LED、泵等具体硬件行为。也就是说，ESP32 既是数据源，也是控制执行端。如果没有这一层，上层系统只能停留在页面展示或算法模拟阶段，无法形成真实的物联网闭环。

## 3. 工程结构说明

工程采用 PlatformIO + Arduino 框架组织，代码按功能模块拆分，便于调试和后续扩展。

当前项目的核心入口位于 `src/main.cpp`，全局配置集中在 `include/config.h`，具体功能模块放在 `lib/` 目录下，测试和调试代码放在 `test/` 目录下。这种结构比把所有逻辑堆在一个主文件中更适合项目交付，因为每个硬件模块、通信模块和控制模块都有相对独立的头文件和实现文件。后续如果需要更换传感器、调整 MQTT 服务器、扩展执行器或优化控制算法，可以在对应模块内修改，而不需要大面积重写主流程。

主要目录作用如下：

- `src/`：主程序入口，负责系统初始化和主循环调度。
- `include/`：集中存放 WiFi、MQTT、主题、引脚、发送周期等配置。
- `lib/wifi/`：WiFi 连接与状态检查模块。
- `lib/mqtt/`：MQTT 安全连接、发布、订阅、回调和重连模块。
- `lib/BH1750/`：BH1750 光照传感器驱动。
- `lib/SoilSensor/`：土壤湿度模拟量采集与滤波模块。
- `lib/ds18b20/`：DS18B20 温度传感器模块。
- `lib/JW01_CO2/`：JW01 CO2 串口传感器解析模块。
- `lib/led/`：WS2812B LED 灯带控制模块。
- `lib/Pump/`：水泵 PWM 控制模块。
- `lib/PidLed/` 和 `lib/PidPump/`：面向灯光和水泵的 PID 控制算法模块。
- `lib/vofa/`：串口波形调试和 VOFA+ 数据输出模块。
- `test/`：独立功能测试、调试说明和历史验证代码。

## 4. 主程序运行流程

主程序负责把各个模块串联起来，形成 ESP32 的完整工作闭环。

系统启动后，ESP32 首先初始化串口、板载 LED、WiFi、MQTT 以及各类传感器和执行器。进入主循环后，程序持续检查 WiFi 状态，维护 MQTT 连接，更新传感器数据，并按照设定的时间间隔发布环境数据。这个主循环是整个 ESP32 端的调度中心，所有功能模块都通过它被周期性驱动。其作用类似现场控制器的大脑：一方面保证设备持续在线，另一方面协调传感器采集、数据上报和硬件响应，避免单个模块阻塞后影响整个系统。

当前主流程可以概括为：

1. 初始化串口、LED、WiFi、MQTT 和传感器。
2. 检查 WiFi 是否在线，断线后尝试重连。
3. 调用 MQTT 主循环，维持连接并处理订阅消息。
4. 更新土壤湿度、光照、CO2 等传感器状态。
5. 按固定周期将传感器数据封装后发布到 MQTT 主题。
6. 根据需要刷新 LED 灯带或执行其他硬件控制逻辑。

## 5. 技术点说明

### 5.1 PlatformIO 与 Arduino 开发框架

简述：本工程使用 PlatformIO 管理 ESP32 编译、依赖和工程结构。

详细说明：PlatformIO 负责定义开发板型号、编译框架、依赖库、串口监视速率和上传参数。相比 Arduino IDE 的单文件开发方式，PlatformIO 更适合多人协作和工程化管理。本项目在 `platformio.ini` 中指定了 `esp32dev` 开发板、Arduino 框架以及 PubSubClient、OneWire、DallasTemperature、FastLED、ArduinoJson 等依赖库。这使得工程可以清晰复现构建环境，也方便后续迁移到其他电脑或交付给队友继续开发。Arduino 框架则降低了 ESP32 硬件操作门槛，让 WiFi、串口、GPIO、I2C、ADC 和 PWM 等功能可以用较直接的方式实现。

### 5.2 模块化代码组织

简述：工程把 WiFi、MQTT、传感器、灯光、水泵和 PID 控制拆成独立模块。

详细说明：模块化是这部分代码的重要工程价值。不同硬件和功能被拆分到 `lib/` 下的独立目录中，例如 WiFi 连接由 `wifi_manager` 管理，MQTT 通信由 `mqtt_client` 管理，传感器各自封装为独立类或函数。这样做可以降低主程序复杂度，让 `main.cpp` 更专注于流程调度，而不是堆满底层读写细节。对于整个项目来说，这种结构有利于后期扩展，例如增加新的空气温湿度传感器、替换 CO2 模块、调整灯带数量、加入自动灌溉策略时，可以在对应模块中扩展，而不会破坏其他功能。

### 5.3 WiFi 网络连接

简述：ESP32 通过 WiFi 接入网络，为 MQTT 通信提供基础连接。

详细说明：WiFi 模块负责根据配置文件中的 SSID 和密码连接路由器，并提供连接状态检查函数。主程序启动时会先尝试连接 WiFi，连接成功后才初始化 MQTT。如果 WiFi 断开，主循环会重新调用连接逻辑并通过板载 LED 状态提示当前网络状态。这个模块在整个系统中非常关键，因为 ESP32 的所有远程数据上报和远程控制都依赖网络链路。若 WiFi 不稳定，上层平台就会表现为数据中断、控制延迟或设备离线。因此 WiFi 连接状态不只是底层细节，而是系统可用性的基础指标。

### 5.4 MQTT 通信机制

简述：ESP32 使用 MQTT 将传感器数据上传到服务器，并接收控制指令。

详细说明：MQTT 是本项目连接硬件端和上层平台的核心协议。ESP32 将采集到的数据发布到传感器数据主题，上层系统、dayu200 或调试客户端订阅该主题后即可获得实时环境数据。同时 ESP32 订阅控制主题，接收类似开灯、关灯、闪烁等控制指令。MQTT 的优势是轻量、适合物联网设备、主题结构清晰，并且可以让多个客户端同时订阅同一类数据。对整个项目而言，MQTT 主题就是软硬件之间的数据契约：ESP32 负责稳定发布，上层系统负责正确订阅和解析。

### 5.5 MQTT over TLS 安全连接

简述：当前 MQTT 连接使用 8883 端口和 TLS 证书校验，提升通信安全性。

详细说明：工程中的 MQTT 客户端使用 `WiFiClientSecure`，并加载 CA 证书来连接 EMQX 服务器。与普通 1883 明文 MQTT 相比，8883 TLS 模式可以避免账号密码和传感器数据在网络中以明文传输。对于比赛或实际部署场景，这一点能体现系统在安全性方面的考虑。尤其当设备连接的是公网 MQTT Broker 时，TLS 可以降低数据被窃听、账号泄露和中间人攻击的风险。需要注意的是，TLS 模式要求服务器证书、域名、系统时间和客户端证书配置匹配，否则可能导致连接失败。

### 5.6 MQTT 主题与数据契约

简述：ESP32 通过固定主题发布数据和订阅控制命令。

详细说明：项目中配置了传感器数据主题和控制命令主题。传感器数据主题用于上报土壤湿度、光照、温度、CO2 和时间戳等字段；控制主题用于接收上层系统下发的设备控制指令。主题命名是整个系统联调时最容易出问题的地方之一，因为 MQTT 主题大小写敏感，多一个字符或少一个路径层级都会导致订阅不到数据。因此该工程把主题集中放在 `config.h` 中管理，便于和 dayu200、服务器规则、可视化端保持一致。上层系统只要遵守这些主题和字段约定，就能稳定接入 ESP32 数据流。

### 5.7 传感器数据采集

简述：工程采集土壤湿度、光照、温度和 CO2 等农业环境关键参数。

详细说明：这些传感器对应智慧农业场景中的核心环境指标。土壤湿度用于判断作物是否缺水，是灌溉控制的基础；光照强度用于判断植物当前接受的光环境，可用于补光控制或环境分析；温度用于反映作物生长环境是否适宜；CO2 浓度用于判断空气质量和温室环境状态。ESP32 作为现场节点，把这些分散的硬件信号统一采集后转换成可传输的数据，使上层系统能够看到实时环境变化。没有这一层采集，项目中的数据展示、趋势分析和自动控制都缺少真实依据。

### 5.8 ADC 模拟量读取与滤波

简述：土壤湿度和光敏测试模块通过 ADC 读取模拟量，并进行平滑处理。

详细说明：ESP32 的 ADC 会受到电源波动、传感器噪声、接线状态和环境干扰影响，原始读数往往会抖动。工程中的土壤湿度模块使用滑动平均思想，把多次采样结果进行平滑，再映射为 0% 到 100% 的湿度百分比。这样可以避免上层系统看到剧烈跳动的数据，也可以降低控制算法误判的概率。对于自动灌溉场景，滤波尤其重要，因为如果湿度读数短时间抖动，水泵可能频繁启停，既影响设备寿命，也会造成控制不稳定。

### 5.9 BH1750 光照传感器

简述：BH1750 通过 I2C 总线采集光照强度，输出单位为 Lux。

详细说明：BH1750 是数字光照传感器，和普通光敏电阻相比，它可以直接输出更标准的光照强度值。工程中通过 I2C 初始化 BH1750，并在主循环或发送数据时读取当前 Lux 值。该模块对整个项目的意义在于提供较可靠的光环境数据，后续可以用于温室补光、植物生长状态评估或环境异常判断。由于它使用 I2C 总线，后期也可以在同一总线上扩展其他 I2C 传感器，但需要注意地址冲突和总线稳定性。

### 5.10 土壤湿度传感器

简述：土壤湿度模块将 ADC 原始值转换为可理解的湿度百分比。

详细说明：土壤湿度传感器的输出通常不是直接的百分比，而是一个与土壤含水量相关的模拟电压。工程中通过干燥值和湿润值两个校准参数，把 ADC 读数映射为 0% 到 100% 的湿度范围。这个转换非常重要，因为上层系统更适合使用业务含义明确的数据，而不是硬件原始读数。湿度百分比可以直接用于页面展示、阈值报警和水泵控制策略。例如当湿度低于某个阈值时，上层或本地控制逻辑可以判定需要浇水。

### 5.11 DS18B20 温度传感器

简述：温度模块使用 DS18B20 采集现场温度，并采用非阻塞更新思路。

详细说明：DS18B20 通过 OneWire 总线通信，温度转换需要一定时间。如果直接阻塞等待，会影响 WiFi、MQTT 心跳和其他传感器更新。工程中的温度模块采用状态机方式发起温度转换，并在转换时间到达后读取结果，尽量减少对主循环的阻塞。这种写法体现了嵌入式物联网项目中的一个重要原则：传感器读取不能长时间占住主循环，否则网络通信和控制响应都会变差。当前 MQTT 发布中温度仍有模拟值使用痕迹，后续可以把真实温度读取接入正式上报字段。

### 5.12 JW01 CO2 传感器

简述：CO2 模块通过 ESP32 的第二串口读取 JW01 数据帧并解析 ppm 浓度。

详细说明：JW01 CO2 传感器通过 UART 输出数据帧，工程中使用 `Serial2` 指定 RX/TX 引脚接收数据，并根据帧头、数据字节和校验和解析 CO2 浓度。串口类传感器和 ADC、I2C 传感器不同，它需要处理数据帧同步、长度检查和校验问题。该模块的价值在于为温室环境提供空气质量和 CO2 浓度指标，后续可以用于通风提醒、环境调控或数据分析。解析逻辑中加入合理范围检查，可以避免异常帧直接污染上层数据。

### 5.13 JSON 数据封装

简述：ESP32 将多路传感器数据封装为 JSON 字符串后发布。

详细说明：JSON 是上层系统非常容易解析的数据格式。工程中发布的数据包含地块编号、土壤湿度、光照、温度、CO2 和时间戳等字段。相比发布多个零散主题，统一 JSON 消息可以让上层一次接收完整环境快照，便于存储、展示和转发。对 dayu200 或 Web 后台来说，只需要订阅一个主题并解析固定字段，就能获得完整数据。需要注意的是，当前时间戳来自 ESP32 的运行毫秒数，不是 Unix 时间；如果上层要做跨设备时间对齐，应由服务器接收时补充标准时间。

### 5.14 定时上报机制

简述：工程通过 `millis()` 控制传感器数据的周期性发布。

详细说明：ESP32 主循环中使用时间差判断是否到达发送周期，而不是简单依赖长时间 `delay()`。这种方式可以让程序在等待下一次上报期间继续维护 WiFi、MQTT 和传感器更新。当前发送周期由配置项控制，便于根据调试或实际部署需求调整。较短的发送周期适合实时调试，但会增加 MQTT 消息量和上层处理压力；较长的周期适合稳定运行和节省资源。对于正式项目展示，可以根据页面刷新频率和服务器承载能力选择 2 秒、5 秒或更长的上报周期。

### 5.15 MQTT 重连与状态保持

简述：MQTT 模块具备非阻塞重连思路，避免连接失败时卡死主程序。

详细说明：网络不稳定是物联网项目中的常见情况。如果 MQTT 连接失败后程序一直阻塞等待，传感器采集和本地控制都会停止。工程中 MQTT 重连逻辑按时间间隔尝试，不会在失败时进入死循环，这让 ESP32 即使暂时连不上服务器，也能继续运行其他任务。连接成功后会重新订阅控制主题，恢复远程控制能力。该机制提升了现场设备的容错能力，也使上层系统在网络恢复后可以重新接收数据。

### 5.16 LED 灯带控制

简述：LED 模块通过 FastLED 控制 WS2812B 灯带颜色和亮度。

详细说明：灯带在项目中可以承担两类作用：一类是作为补光设备或执行器，参与农业环境控制；另一类是作为调试和状态显示设备，帮助开发者判断系统运行状态。工程中封装了设置全灯颜色、设置亮度和运行彩虹效果等功能。由于 WS2812B 是可编程灯珠，后续可以根据光照传感器数据自动调节亮度，也可以根据 MQTT 指令切换颜色或模式。它让项目不仅能采集数据，还具备直接改变现场环境的能力。

### 5.17 水泵 PWM 控制

简述：水泵模块通过 LEDC PWM 输出控制水泵转速或开关强度。

详细说明：水泵控制是智慧农业闭环控制的重要执行环节。土壤湿度传感器负责判断土壤是否缺水，而水泵模块负责真正执行补水动作。工程中使用 ESP32 的 LEDC PWM 功能输出占空比，并对输出范围做了限制，避免过高输出造成设备风险。虽然当前主程序中水泵部分处于注释或调试状态，但模块已经具备后续接入自动灌溉逻辑的基础。正式使用时，需要结合继电器、MOS 管或驱动模块，并根据硬件接线确认高低电平逻辑。

### 5.18 PID 控制算法

简述：工程为灯光和水泵分别准备了 PID 控制模块。

详细说明：PID 控制用于根据目标值和当前测量值之间的误差计算输出量。对于灯光控制，可以根据目标光照和实际光照差值调节 LED 亮度；对于水泵控制，可以根据目标湿度和当前湿度差值调节水泵输出。工程中的 PID 模块包含比例、积分和微分项，并加入输出限幅和一定的微分平滑处理。它的意义在于让系统从简单的“阈值开关”升级为连续控制，避免设备频繁启停，使环境调节更加平稳。不过 PID 参数需要结合真实硬件调试，不能只依靠默认值。

### 5.19 串口调试与 VOFA+

简述：VOFA 模块用于通过串口输出多通道数据，辅助观察控制曲线。

详细说明：在调试传感器和 PID 控制时，单纯看串口文本很难判断数据变化趋势。VOFA+ 可以把串口输出的浮点数据绘制成曲线，帮助开发者观察目标值、当前值、PWM 输出和环境扰动之间的关系。工程中的 VOFA 模块提供了波形生成和多通道数据发送功能，适合验证 PID 控制是否稳定、传感器滤波是否有效、输出是否过冲等问题。对于比赛项目展示，这类调试工具也能说明团队不是只做了功能堆叠，而是有控制算法调试和数据验证过程。

### 5.20 本地状态指示

简述：板载 LED 用于提示 WiFi、MQTT 或系统运行状态。

详细说明：嵌入式设备调试时，串口并不总是方便查看，尤其设备部署到现场后，最直接的状态反馈往往来自指示灯。工程中使用板载 LED 表示连接过程、连接成功、重连等状态。虽然这是一个小功能，但对排查问题非常实用。例如设备无法上报数据时，可以先通过 LED 判断是 WiFi 没连上、MQTT 没连上，还是程序已经运行但服务器侧订阅有问题。它降低了现场调试成本。

## 6. 与上层系统的协作关系

ESP32 端为上层系统提供实时数据源，并接收上层系统的控制指令。

上层系统可以是云服务器、EMQX Broker、dayu200 设备、Web 后台或移动端。ESP32 通过 MQTT 把传感器数据发送到 Broker，上层系统订阅后进行显示、存储、分析或报警。当上层系统需要控制现场设备时，再向控制主题发布命令，由 ESP32 接收后执行。这个结构让系统具备典型物联网架构：设备端负责采集和执行，服务器负责转发和管理，应用端负责展示和交互。ESP32 的稳定性直接影响上层系统看到的数据质量和控制体验。

## 7. 当前工程状态与注意事项

当前主固件路径已经具备完整的采集、联网、发布和部分控制能力。

需要注意的是，`test/` 目录中有些测试文件保留了早期接口，例如旧版 MQTT 测试仍可能调用无参数的数据发送函数。这类文件更适合作为历史调试记录，不应直接代表当前主固件逻辑。正式整理项目时，可以把仍然有效的测试用例保留，把接口过期的测试代码更新或移动到历史目录。另外，配置文件中包含 WiFi 和 MQTT 账号信息，项目公开展示或提交到公共仓库前应替换为占位符或改为本地私有配置，避免泄露连接凭据。

## 8. 后续优化方向

工程后续可以从稳定性、安全性、控制闭环和项目展示四个方面继续完善。

第一，可以把温度真实读取接入正式 MQTT 数据包，减少模拟数据残留。第二，可以将发送周期调整到更适合展示和服务器处理的范围，避免 500 ms 高频上报给接收端造成压力。第三，可以把 LED 和水泵控制从简单回调扩展为完整的 JSON 指令解析，例如支持目标亮度、目标湿度、模式切换和手动/自动控制。第四，可以增加本地缓存或断线重发策略，提高网络波动时的数据可靠性。第五，可以把敏感配置从源码中剥离，改为单独的私有配置文件或编译宏，提升项目交付安全性。

## 9. 总结

ESP32 工程是整个项目的硬件接入层、数据采集层和边缘执行层。

它把农业现场的真实环境数据转换成上层系统可使用的 MQTT 消息，也把上层系统的控制意图转换成具体硬件动作。项目中的传感器采集、网络通信、安全连接、JSON 数据封装、执行器控制和 PID 调节都围绕这一目标展开。对于完整项目而言，这部分代码的价值不只是“让 ESP32 能跑”，而是让整个系统从软件展示变成真实可感知、可控制、可联动的物联网系统。
